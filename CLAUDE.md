## Architecture in one minute

pnpm monorepo (Node 24, pnpm 9.15.4, TypeScript, ESM). Express API (`server/`) serves the React/Vite board UI (`ui/`) on one port, 3100. Data lives in Postgres through Drizzle (`packages/db/`); with `DATABASE_URL` unset it uses embedded Postgres, so no database setup is needed. Agents run through adapters (`packages/adapters/*`) and the native Runner (`packages/paperclip-runner/`, TypeScript plus a **Rust** daemon, toolchain pinned to 1.97.1 in `rust-toolchain.toml`). The `paperclipai` CLI (`cli/`) is what installs, runs and services an instance. Full repo map: `AGENTS.md` section 3.

Instance state is never in the repo. It lives in `~/.paperclip/instances/<id>/` (`config.json`, `.env`, `db/`, `data/backups/`, `secrets/master.key`, `workspaces/`, `logs/`). Override with `PAPERCLIP_HOME` and `PAPERCLIP_INSTANCE_ID`.

## Build and run locally (for testing changes)

Prerequisites: Node >= 24.11 (`.nvmrc` says 24), pnpm 9.15.4 (`corepack enable`). The docs target macOS, Linux and WSL2; **native Windows for the full dev loop is not documented, so use WSL2 or Docker** (not yet verified on our machines).

```sh
pnpm install
pnpm dev                      # API + UI at http://localhost:3100, watch mode
pnpm dev:once                 # same, no file watching, auto-applies pending migrations
pnpm dev --data-dir ./tmp/pc  # isolated state, so you never touch another instance's data
pnpm dev:list / pnpm dev:stop # inspect / stop the dev runner (add the same --data-dir)

curl http://localhost:3100/api/health
rm -rf data/pglite && pnpm dev   # reset the dev DB per AGENTS.md; the embedded DB itself lives under ~/.paperclip/instances/<id>/db (or your --data-dir)
```

`pnpm dev` defaults to `local_trusted` (no login, loopback only). To test the login-required mode the VM uses, run `pnpm dev --bind lan`.

Verify (from `AGENTS.md` section 7):

```sh
pnpm verify                   # affected Vitest files only; exit 2 means "needs broader checks", not failure
pnpm -r typecheck             # or: node scripts/typecheck-low-memory.mjs
pnpm build                    # needs the Rust toolchain for the Runner binary
pnpm check:token-gates        # required for any ui/ change (design tokens only)
node scripts/agent-preflight.mjs   # prepares a fresh worktree (install + Runner build, cached)
```

DB schema change: edit `packages/db/src/schema/*.ts`, export from `schema/index.ts`, run `pnpm db:generate`, then `pnpm -r typecheck`.

## Deploy to the Azure VM

**Follow `doc/DEPLOYMENT-STEPS.md`.** It has the full procedure: push, read-only GitHub token, VM checks (Node, Rust, swap, outbound access), backup, `install --repo ... --ref <sha>`, verification, rollback, later updates, and troubleshooting.

Key facts to keep in mind:

- VM: `vm-paperclip-westus-001`, subscription `sb_sbxquetz_joshf`, VPN-only (details in `../PAPERCLIP-PILOT.md`). Paperclip runs as a systemd user service behind Caddy (HTTPS on 443, Paperclip on loopback 3100). Instance data is in `~/.paperclip/instances/default`.
- The VM was set up with the **upstream npm release**. The fork is deployed with the managed git-ref install, which builds from GitHub, so only **pushed** commits can be deployed. The first deploy is untested; record the result in section 11 of `doc/DEPLOYMENT-STEPS.md`.
- Deploy a commit SHA the first time, take `paperclipai db:backup` first, and roll back with `paperclipai update --rollback` (the database is not rolled back).
- Telemetry is disabled in the instance `config.json` (`telemetry.enabled = false`). Re-check after any install.
- In-repo plugins listed in `scripts/shipped-plugins.json` (the ADO plugin) are installed and updated by the deploy itself, and roll back with the payload: see "How in-repo plugins ship" in `doc/DEPLOYMENT-STEPS.md`.
- Fallback if the git install cannot work on the VM: build the Docker image (`Dockerfile`) and run it there. That replaces the service-based setup, so decide deliberately.

## Working rules for this build

- **Lockfile: keep `pnpm-lock.yaml` and commit it with any dependency change** (run `pnpm install`, then commit the result). The Docker build copies it, and the VM's git install runs `pnpm install --frozen-lockfile`, which fails if it is missing or stale. Deleting it would also let every build resolve different dependency versions, which can break the pinned patches in `patches/` and the overrides in `pnpm-workspace.yaml`.
- **Line endings must be LF in the working tree.** A CRLF Windows checkout breaks the Docker build. The fix (`git config core.autocrlf input` and re-checkout) is in `doc/LOCAL-DOCKER.md` and is already applied on Josh's machine. Don't commit line-ending-only changes.
- **Fork patches to upstream code, keep them when editing nearby:** (1) `packages/paperclip-runner/src/drivers/acpx/installation-integrity.ts` accepts the workspace pnpm store (`<root>/../node_modules/.pnpm`) as part of the provider root, because the Docker and git-install layout is a pnpm workspace; without it onboarding a Claude agent fails with "resolves outside the selected provider root". (2) `server/src/lib/agent-runner-platform.ts` waits 5 s (was 1 s) for libc detection, so a slow boot doesn't disable the native Runner. (3) `scripts/prepare-bundled-package.mjs` builds `server/ui-dist` and falls back to the repo-level `skills/` folder when the server package lacks them, because the managed git install calls that script directly and skips the server's `prepack` hook and upstream's release copy step; (4) `server/src/routes/health.ts` exposes `serverVersion` on the redacted health response so `paperclipai update` can validate the restarted service. (5) `packages/plugins/sdk/src/worker-rpc-host.ts` rebuilds `ctx.http.fetch` responses with a null body for 204/205/304, because `new Response("", {status: 204})` throws and broke every plugin `ctx.http.fetch` call that gets an empty success (found while building the ADO plugin). (6) ADO links (A2): `packages/shared/src/issue-creation-source.ts` (`LINKED_TASK_ORIGIN_KINDS`) keeps a task with origin `plugin:chimera.plugin-ado:workitem` an ordinary task for creator visibility and for recovery (`server/src/services/recovery/successful-run-handoff.ts`); `server/src/services/task-search.ts` matches `origin_id` of those origins only, so `123`, `#123` or `org/project/123` finds the linked task; `server/src/services/plugin-host-services.ts` (and the SDK test harness) let a plugin move a task only between `manual` and its own origin namespace, in both directions (upstream let it relabel any task into its namespace); the task list has a "Linked to ADO" filter (`ui/src/lib/issue-filters.ts`, `IssueFiltersPopover`, `IssueFilterPanel`, `IssuesList`, `LegacyIssuesList`, `pages/Issues.tsx`, `pages/CoordinatorTasks.tsx`, exact `originKind` in the URL). (7) In-repo plugins ship with the code: `scripts/shipped-plugins.json` lists them; `scripts/prepare-bundled-package.mjs` (via `scripts/shipped-plugins.mjs`) builds each one and stages a copy inside the server package for the managed git install, the `Dockerfile` builds them in place, and `server/src/services/shipped-plugins.ts` (called from `app.ts` before `loadAll`, self-hosted only) installs each listed plugin or rebinds an existing install of the same key to the copy that ships with the running server, auto-approving its capabilities; unlisted plugins are untouched. Details in `doc/DEPLOYMENT-STEPS.md`, "How in-repo plugins ship". (8) Tools of shipped plugins are allowed for agents by default: `server/src/services/tool-access-policy.ts` returns `allow_shipped_plugin` just before `deny_default`, for plugin keys `shipped-plugins.ts` reconciled (`shippedPluginKeys()`) whose plugin is ready; the gateway passes the providing plugin as `request.pluginId` (`tool-gateway.ts` `policyInputForAgentTool`; new field and reason code in `packages/shared/src/types/tool-access.ts`). See "Agent tool access" under "How in-repo plugins ship". (9) Backlog view (`doc/plans/2026-11-17-backlog-view.md`): new pages and components live in `ui/src/pages/Backlog*.tsx`, `ui/src/components/backlog/`, `ui/src/lib/backlog/`, `ui/src/api/backlog.ts`, `ui/src/hooks/useBacklog.ts`; the upstream files touched are the three sidebars (`Sidebar.tsx`, `Sidebar.production.tsx`, `CoordinatorSidebar.tsx`, Backlog below Tasks when `chimera.plugin-ado` is ready), `App.tsx` routes, `lib/company-routes.ts` (`backlog` route root, so links get the company prefix), `lib/queryKeys.ts` (`backlog` keys), and `pages/IssueDetail.tsx`, whose `useTaskDetailInterfaceMode` moved unchanged to `ui/src/hooks/useTaskDetailInterfaceMode.ts` so the work item page picks the same task thread component. (10) Shipped plugins may nest tasks at any depth: `server/src/services/plugin-host-services.ts` (`pluginParentDepthPolicy`) passes `parentDepthPolicy: "allow_nested"` to `issues.create`/`update` when the calling plugin is the shipped copy (`isTrustedShippedPluginRecord` in `shipped-plugins.ts`, also used by `tool-access-policy.ts`); every other plugin keeps upstream's agent depth rule (`doc/plans/2026-11-05-two-level-task-hierarchy.md`). The ADO plugin needs this so the task tree mirrors ADO (Feature → Story → review Task). (11) Plugin tools are reached only through `GET /api/plugins/tools` and `POST /api/plugins/tools/execute`, not as native or MCP tools, and upstream's `paperclip` skill never said so, so agents could not find the ADO tools. The fork adds `skills/paperclip/references/plugin-tools.md` and one sentence pointing to it, appended to an existing line under "Key Endpoints" in `skills/paperclip/SKILL.md`. Do not add lines or headings to that SKILL.md: `packages/paperclip-runner` pins its headings by line number in generated contracts (`generate-capability-contract.mjs` and the checks after it), and the server build fails on drift. New reference files are not indexed unless listed in `packages/paperclip-runner/spec/capability/source-contract.json`. Also `server/src/routes/plugins.ts`: `POST /api/plugins/tools/execute` takes `runContext` from an agent's run token when the agent omits it, and `server/src/routes/openapi.ts` marks it optional and describes both plugin tool routes so `search_api` finds them (agents on Haiku guessed other routes). (12) `server/src/services/native-runtime/status-arbiter.ts` (input `externalItemWakesTask`, set in `native-run-finalizer.ts` from `isLinkedTaskOriginKind`): a native run on a task linked to an ADO work item that finishes `yielded` with a `response_wake` continuation is parked `in_review` (reason `external_item_response_waiting`, no effects) instead of being re-run at once. Upstream re-runs such a wait unless a person's comment started the run, which looped an agent waiting for Josh's approval every few seconds; for linked tasks the ADO plugin wakes the agent when the item or its pull request changes. (13) `server/src/services/native-runtime/external-review-wait.ts` (`listLinkedItemReviewWaits`, appended to `listExternalReviewWaits`): an `in_review` task linked to an ADO work item, with an agent assignee, counts as a maintained `external_response` review path. Without it Paperclip's review-path recovery saw no path, woke the agent with `issue_review_path_lost` and then blocked the task for a board decision, which cleared the task's execution run and revoked the running agent's tool binding (`paperclip_runner_tool_binding_not_authorized`), so Maple could not move her work item back to In Review after fixing review findings. The same list feeds review attention in `issues.ts` and `hasPersistedDurableWaitPath` in `recovery/service.ts`. Also in `prepare-bundled-package.mjs`: it resolves `workspace:*` dependencies to each package's own version (plugin-sdk is 1.0.0, not 0.3.1), it also strips `prepack`/`postpack` from the staged manifest, because `npm pack` runs them outside the workspace and fails. Without these changes `paperclipai install --ref` fails with `ENOENT ... server/ui-dist` or `server/skills`, or in `npm pack`. (14) `server/src/services/heartbeat/queue.ts` (`shouldQueueFollowupForRunningIssueWake`): a plugin wake (its context carries `pluginId`) arriving while the assignee's run on the same task is running is deferred to a new turn instead of merged into the running one. Merged, it was lost: in the #827 test the Review's Approved wake landed while Maple was in a run started by the reviewer's comment a second earlier, so she never moved the Story to Ready To Merge. Test in `server/src/__tests__/heartbeat-running-followup.test.ts`. (15) Run ledger sessions: `describeSessionStart` in `server/src/services/heartbeat/run-state.ts` records why a run resumes or starts a session (`contextSnapshot.paperclipSessionStart`, set in `heartbeat.ts` after the session is resolved); `runsForIssue` in `server/src/services/activity.ts` returns `sessionId`, `sessionStartReason`, `sessionResumedTaskSession` and `sessionEvent` (the provider's `session.started` / `session.resumed` event); `ui/src/components/IssueRunLedger.tsx` (`groupRunsBySession`) shows each run's session and a header per agent session with its run count and why it started. Asked for by Josh after sessions ended with no visible reason. Tests in `server/src/__tests__/session-start-reason.test.ts` and `IssueRunLedger.test.tsx`. (16) Cost breakdown for plugins: `getIssueCostSummary` in `server/src/services/plugin-host-services.ts` also returns `breakdown`, the same cost totals grouped by agent, provider, model and billing type (`PluginIssueCostBreakdownRow`, optional `breakdown` on `PluginIssueCostSummary` in `packages/plugins/sdk/src/types.ts`; the SDK test harness returns `[]`). The ADO plugin's cost per Feature (D9) prices subscription tokens at API rates per model, which the totals alone cannot do. Test added to "narrows orchestration cost summaries" in `server/src/__tests__/plugin-orchestration-apis.test.ts` (embedded Postgres refuses to run as root: run it as another user).
