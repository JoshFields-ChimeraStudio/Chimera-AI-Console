# ADO integration: A1 decisions

Outcome of backlog item A1 (`doc/BACKLOG.md`). This note records how the integration is built; the backlog stays the list of what is left to do. The code is in `packages/plugins/plugin-ado`.

## Decisions

1. **A Paperclip plugin** (`chimera.plugin-ado`), not a curated connection and not MCP-only. Plugins get typed events, secret-ref config, agent tools, their own database schema and UI slots, which covers A2 to A8.
2. **Plain ADO REST API (version 7.1), not the ADO MCP server**, inside the plugin. Code-driven sync needs exact control over revisions, retries and throttling, and the hosted ADO MCP server only supports interactive sign-in. Agents keep the ADO MCP server until the A8 tools reach parity.
3. **Inbound events: ADO service hooks send to an Azure Service Bus queue, and the plugin listens on it.** Basic tier namespace `sb-paperclip-westus-001`, queue `ado-events`, resource group `rg-paperclip-westus-001` in the sandbox subscription.
   - **Why Service Bus, not a Storage queue** (the first choice): the plugin keeps one outbound connection open (AMQP on port 5671) and Service Bus delivers each message over it as it arrives. Nothing polls, events land in seconds, and nothing on the VM is exposed. A Storage queue can only be polled, and a plugin job can run at most once a minute. Service Bus also locks a message while it is handled, redelivers on failure and moves it to a dead-letter queue after too many failures (we set 20), so failures stay visible. Messages can be up to 256 KB rather than 64 KB. Cost on Basic is about $0.05 per million operations.
   - **Rejected:** a relay or Event Grid push (both need a public endpoint), and the Storage queue (polling only).
   - **Access:** two queue-level shared access policies. ADO gets `ado-send` (Send only); the plugin gets `plugin-listen` (Listen only), stored as a secret.
   - **ADO subscription settings:** one subscription per event type (ADO allows only one), all to the same queue, created **signed in as the service account**, because ADO disables a subscription when its creator leaves the project. Tick **"Send as non-serialized string"** (bypass serializer), otherwise the body arrives wrapped in .NET serialization. Resource details to send: **All** (fits within 256 KB, and the plugin re-reads the item anyway; this avoids depending on what the minimal payload contains). The parser still falls back to the id in the resource URL and warns about any event it cannot place.
   - **Network:** the VM and local Docker need outbound TCP 5671 to `*.servicebus.windows.net`. If that is ever blocked, the SDK can use WebSockets on 443 instead.
4. **Messages are signals, not data.** On every message the plugin re-reads the work item or PR from ADO, because ADO drops events while a subscription is failing ("probation") and events can arrive out of order. To cover what was missed, the plugin runs a **catch-up**.
5. **Catch-up runs on startup and from a "Sync now" button, never on a timer.** It runs once per company when the worker starts with that company's settings (including after a crash restart, and the first save after install), and whenever someone presses **Sync now** on the Azure DevOps dashboard widget. Sync now only starts it; the catch-up runs in the background and the widget refreshes until it ends. It asks ADO for work items changed since the last successful catch-up (WIQL on `System.ChangedDate` with `timePrecision=true`; the first run looks back 7 days), 5,000 at a time ordered by change date (WIQL refuses more than 20,000), reading ADO as it was when the catch-up started (`ASOF`) so edits made meanwhile cannot make it skip items, fetches them 200 at a time and handles each through the same code path as a live event. The watermark moves forward after each full page and to the start time (less one minute of overlap) when the catch-up completes. A second press while one is running is refused. If the startup catch-up fails, it runs again on the next settings save. Lost events can therefore go unnoticed until the next restart or a manual sync; the listener status on the widget and the plugin health check show when events are failing.
6. **The task-to-work-item link (for A2) uses both mechanisms:**
   - On the task: `originKind = "plugin:chimera.plugin-ado:workitem"`, `originId = "<org>/<project>/<id>"`. This is the indexed key for "does this ADO item already have a task?". Nothing enforces uniqueness, so check with `issues.list({ originKind, originId })` before creating. Do not use an origin kind ending in `:operation`, because those are hidden from task lists.
   - In the plugin's own database schema: an `ado_links` table (issue id, org, project, work item id, type, state, url, rev, last synced) for the changing state and reverse lookups.
   - Limit: one ADO work item per task, which matches A2.
   - **As built (A2):** the table is `ado_links` in schema `plugin_ado_3dc5cc6a90` (`migrations/001_ado_links.sql`), keyed by issue id with a unique (company, org, project, work item id); it also stores the title and a `missing_at` mark. `org` is the organization name from the URL. Only tasks with origin `manual` can be linked, so a routine run or another plugin's task is never taken over; unlinking sets the origin back to `manual`. The host now lets a plugin move a task only between `manual` and its own origin namespace, so no plugin can relabel a routine run and then hand it back as `manual`. The "already linked" message names the other task by identifier only, and a concurrent link of the same item (unique violation on insert) gets the same message. Changing the organization URL or project in settings orphans existing links: they keep their old org/project and are no longer refreshed or found by search, and nothing migrates them. Overwriting the origin had two side effects that core now prevents, because nearly every task will be linked once A3 lands: core treated any `plugin:` origin as agent-created (hidden from the default task list) and as plugin-managed (stranded-run recovery skipped it). Fork patch 6 in `CLAUDE.md` lists the core changes.
   - **Not used: Paperclip's external objects** (`external.objects.*`). They are detected from URLs mentioned in a task's text and comments and shown as status pills, with a status filter. A plugin cannot attach one to a task directly, a task can mention many, and they are not searchable by ID, so they do not fit "this task is that work item". They could later show ADO items or PRs that are only mentioned in a task (a candidate for A5).
7. **Rate limits:** all agents share one PAT, so ADO counts them as one identity: about 200 throughput units per 5 minutes. The client honours `Retry-After` (seconds or a date) once on 429/503. The listener handles one message at a time. The A8 tools must tell the agent when they are throttled rather than retrying silently.
8. **Loop prevention (for A4):** ignore events whose `System.ChangedBy` is the service account (config field `serviceAccountName`). Every write uses a `test /rev` operation first in the JSON Patch so concurrent edits fail instead of overwriting.
9. **PAT scopes:** Work Items (Read & write) and Code (Read & write). No Service Hooks scope; the subscriptions are created by hand.
10. **Secrets:** the PAT and the listen-only connection string are secret-ref settings. The host limits secret lookups per minute, so the worker keeps the PAT in memory for at most a minute (never logged or stored) and drops it on a 401. The Service Bus client holds its connection string for as long as the listener runs.

## How the plugin runs

- **Settings per company:** organization URL, project, PAT (secret), Service Bus connection string (secret, listen only), queue name (default `ado-events`), service account display name.
- **Listener:** the host delivers each company's saved settings when it loads the plugin and on every save (`onConfigChanged`; the plugin sets `multiCompanyConfig`). The plugin then (re)starts that company's listener, one start or stop at a time per company; callbacks from a replaced listener are ignored. The host does **not** replay settings when it restarts a crashed worker, so on every start the plugin also lists companies and applies any saved settings the host has not delivered (needs `companies.read`; retried a few times because the host refuses that call while another call to the worker is in flight). The Service Bus SDK reconnects by itself after errors; the error is shown until a message gets through again.
- **Background work and host permissions:** calls the worker makes inside a host call (a settings delivery, a button press) carry that call's id, and the host refuses them once that call has returned. The listener and the catch-up are therefore started through an `AsyncResource` created at module load, so their calls carry no id and the host treats them as background work for companies with saved settings.
- **Message outcomes:** handled → completed. Unreadable → dead-lettered at once. Work item not found (404) → completed with a warning. Any other failure → held for 10 seconds per attempt (at most 50; the SDK renews the message lock meanwhile) and then abandoned, so Service Bus redelivers it; with a maximum delivery count of 20 an ADO outage of about 15 minutes is ridden out before messages are dead-lettered. The listener handles one message at a time, so this also slows it down while ADO is failing. PR events wake the agent (below).
- **Pull request events (first part of A5, `src/pullrequests/`):** on any pull request event the plugin re-reads the PR, its linked work items and its comment threads, and compares them with what it recorded for that PR in plugin state (company scope, key `pr:<repositoryId>:<id>`: last status and every comment already seen). When the PR has become **completed** or **abandoned**, or someone has added a comment to an **active** PR, it posts a comment on the Paperclip task linked to each of the PR's work items (with the PR link, branches, and for comments the author, file, line, thread and text) and wakes the task's agent (reasons `ado_pull_request_completed`, `ado_pull_request_abandoned`, `ado_pull_request_comments`). Not new work: ADO's system comments (votes, pushes), blank comments, comments on a closed PR, and, for each agent, its own comments (agents sign their PR comments `[<agent name>]`); all are still recorded as seen. Tasks with no agent or cancelled are skipped; a `done` or `backlog` task is set back to `todo` first, because the host cannot wake those. The record is saved after the notices, so a failed notice is retried on redelivery; a failed wakeup is only logged (the comment is already on the task). Status changes are announced once, and the first event seen for a PR announces its existing people's comments. Not yet: showing the PR on the task, reviewer votes, policy checks, and clearing blockers on merge.
- **ADO drives the task (`src/watch/`, November 2026):** agents should work like people on a team: they do not close a task and ignore what comes after. For a work item with a linked task:
  - **Closing.** The task is closed by the plugin when the work item reaches `Completed` (done) or `Removed` (cancelled). If the task is marked done while the work item is still open, the plugin puts it back to `in_review` (or `blocked` when the work item is `Blocked`), with a comment saying it closes by itself (checked on `issue.updated`, against the live ADO state).
  - **Others' changes wake the agent.** On every work item event (and catch-up), the plugin reads the item's history (updates API) and comments after the last revision it handled (plugin state `wi-watch:<id>`; the first time, the link's revision and sync time before the event). Changes by anyone other than the agent on the linked task are posted on the task and wake it (reason `ado_work_item_changed`, a done task reopened to `todo` first): state changes, comments, and edits to title, description, acceptance criteria and technical notes. All agents write as the service account, so an agent's change is told apart by the `agent:<Name>` tag written with it (carried over revisions that do not touch the tags), and an agent's comment by its `[Name]` prefix. This replaced the old rule that ignored every event caused by the service account.
  - **Roll-ups.** When a child reaches Completed or Removed, the plugin completes its parent if the parent is a Feature, Epic or Documentation item In Progress and every child is final (one Completed at least). The change is rev-guarded; a conflict is left for the next event. Owners of those types hear about a child only when it is Blocked.
  - **Children report to their parent's owner.** A state change of a work item by anyone other than the agent on its parent's linked task wakes that agent (reason `ado_child_changed`): a Review approved or asking for changes, a QA Test passed or failed, a Defect filed or fixed, a Story completed under a Feature. A child with no linked task is read only on live events and only when its parent has an agent, so syncs do not replay old changes. Handing an item over (`Ready For Review`, `Ready For Test`, `Ready For Retest`) wakes its assignee by the rule above. See "Who owns what" in `doc/plans/2026-11-17-agent-workflow.md`. This replaced the November 2026 re-review wake on `Changes Requested` → `In Review`.
  - The record is saved after the notices, so a failed notice is retried on redelivery; a failed wakeup is only logged.
  - Pull request comments: an agent is no longer spared other agents' comments, only its own (`[Name]`-signed). New comments also go to the agents on unfinished Reviews under the PR's work items (reason `ado_pull_request_review_comments`), so a reviewer sees the builder's replies.
  - **Parked, not lost.** A linked `in_review` task counts as a maintained review path for Paperclip's recovery (`CLAUDE.md` fork patch 13), so recovery no longer blocks it for the board while the agent waits on ADO.
  - **Who made a change.** A revision is an agent's when the history the tools write in it is signed `[Name]`, or it changes the `agent:<Name>` tag; failing both, when ADO reports the configured service account (then the agent its tag last named). Comments: signed `[Name]` is that agent. So a mistyped "Service account display name" setting no longer makes an agent's own changes wake it (it did for Rowan: ADO reported the PAT's account, "Josh Fields AI Team").
  - **Waiting.** An agent with nothing to do until someone else acts ends its run with `paperclip_finish`, `yielded`, `response_wake`. On a linked task the server parks that in review (`CLAUDE.md` fork patch 12) rather than re-running it; the plugin's wakeups are what resume it. Agents never finish linked tasks with `done` and never poll.
- **Dashboard widget "Azure DevOps":** listener status, last event, last catch-up, and the Sync now button.
- **No scheduled jobs.**
- **Tests:** `pnpm --filter @chimera/plugin-ado test` (decoding, client retry and PAT redaction, WIQL and batching, listener lifecycle, startup catch-up, Sync now, message outcomes, health, agent tools and roles; links against an in-memory repository, because the test harness has no database).

## A8: agent tools

Code in `src/tools/` (declarations shared by the manifest and the worker, the role table in `roles.ts`). Every tool that writes has a write verb in its name, because the host rates a tool's risk from its name (`inferToolRisk` in `server/src/services/tool-gateway.ts`) and may run "read" tools without approval. All agent writes to ADO go through these tools; the ADO MCP server stays in agent configuration until parity is confirmed in use.

Roles, tool rights per role, and the workflow rules the tools enforce (who assigns, who creates which type, who sets which state) are in `doc/plans/2026-11-17-agent-workflow.md`, the single source; the code is `src/workflow/` and `src/tools/roles.ts`. Tools: `ado_get_work_item` (fields, relations summary, recent comments), `ado_get_workflow` (the rules), `ado_post_comment`, `ado_update_state`, `ado_create_pr_link` (repo name or ID + PR number), `ado_create_work_item` (replaced `ado_create_child_work_item`) and `ado_update_assignment`. Pull request tools (A9, November 2026): `ado_create_pull_request` (repository, source and target branch, title, description, work items to link; returns the open pull request instead of a second one), `ado_get_pr_threads` (a read tool: the pull request and its threads, without ADO's system notes unless asked) and `ado_post_pr_comment` (a new thread, optionally on a file and line, or a reply with `threadId`; `status` sets the thread status). Comments are signed `[Name]` like work item comments, and every write is in the activity log. Agents keep `ADO_GIT_PAT` only for git (clone, fetch, push).

- **Roles:** the `agentRoles` setting maps an agent name (case-insensitive) to a role; agents not listed are readonly. Names are unique only among live agents, so the first agent to use a name is bound to it (trust on first use, kept in plugin state); another agent later given that name is readonly and told why. Remove the entry, save and re-add it to rebind, or set the entry's optional `agentId`, which always wins. Denials come back as a tool error naming the role and what it allows.
- **Caller identity:** the host checks that the run id belongs to the calling agent and company, but not that the run is still active, and the SDK cannot look a run up by id. So a board user calling the tool-execute endpoint directly can act as an agent using an old run id; acceptable while Josh is the only board user.
- **Default work item:** the tool context carries no task, so the plugin finds the agent's task whose `executionRunId` (preferred) or `checkoutRunId` is the calling run, then uses its A2 link. Without a task or link the tool asks for the ID.
- **Attribution and audit:** every comment and history entry starts with `[AgentName]`; every write goes to the activity log (on the run's task when known) with agent, run, role, work item and action in the metadata.
- **Safety:** updates start with `test /rev`; a conflict (409/412) tells the agent to re-read. Agent text is HTML-escaped with line breaks kept. `ado_update_state` checks the target against the type's states (cached 10 minutes) and lists them on error, then the workflow's state rules. A 429 after the client's one retry returns "ADO is throttling, try later"; a 503 returns "ADO is unavailable, try later". Adding a comment and creating an item are never retried on 503 (the first attempt may have gone through), only on 429 with `Retry-After`. New items inherit the parent's area and iteration.
- **Who creates what (Josh, November 2026):** now the creation table in `doc/plans/2026-11-17-agent-workflow.md`. Bugs are for problems found in production or deployed code. A failed review goes back through the PR comments and the story's state, not a new item.
- **Last touched by (A7):** every write also sets the tag `agent:<Name>` and removes any earlier `agent:` tag, so the item shows which agent changed it last. Comments use a separate API, so after a comment the tag is set in its own small update (skipped when it is already right; best effort, because the comment is already posted).
- **State rules (A4):** enforced by `ado_update_state` (and the assignment and creation rules by their tools), from `src/workflow/`; see `doc/plans/2026-11-17-agent-workflow.md`. Automatic roll-ups and the Paperclip-to-ADO state sync of A4 are still open.
- **Setup:** none in the host: tools of shipped plugins are allowed for agents by default ("Agent tool access" under "How in-repo plugins ship" in `doc/DEPLOYMENT-STEPS.md`), so the `agentRoles` setting decides what each agent may do.

## D4: what waits for Josh

A global toolbar button from the plugin ("ADO · N need you", `AdoNeedsJosh` in `src/ui/index.tsx`) lists the work items waiting for Josh, oldest first, each with what he is asked to do and links to the Backlog page and to ADO. The list is the plugin's `needs-josh` data, read from the work item cache (no ADO calls), using `JOSH_WAITS` in `src/workflow/rules.ts`:

| Type | State | Josh is asked to |
|---|---|---|
| Epic | Plan Review | approve the plan (set the Epic In Progress) |
| Feature | Ready For Approval | approve the breakdown (set the Feature Ready For Work) |
| User Story, Bug | Ready To Merge | review and merge the pull request |
| Document | In Review | review the document's pull request |
| any type | Blocked | answer the question |

The button refreshes every 30 seconds. With Josh's permission (a button in the list), the browser shows a Windows notification for each new wait while any Paperclip tab is open; clicking it opens the item's Backlog page. What has been seen is kept per browser (localStorage), so the first load and reloads do not notify again. Notifications with every tab closed would need a service worker and web push, which is not built. Waits from Paperclip itself (approvals, failed runs, budget stops) are the rest of D4.

## A10: the smoke-test Epic

A dashboard widget, "Azure DevOps smoke test" (`AdoSmokeTest`, worker code in `src/smoke/`), on only when the **Smoke-test agent** setting names an agent.
- **Start** creates an Epic "Smoke test: full workflow (<time> UTC)" with the standard description and acceptance criteria (`smokeDescription`, the one copy). Each run names a new file to add (`smoke/hello-<yyyymmdd-hhmmss>.txt`, from the creation time), so a run never finds the previous run's file already on main. It assigns the Epic to the smoke-test agent through the Backlog view's assignment path, as the board user who pressed it. The Epic's ID is kept in plugin state (`smoke-test-epic`).
- If a smoke test already exists, Start first does Clean up, and creates nothing if any item could not be closed.
- **Clean up** walks the Epic's tree (at most 200 items) and sets every item that is not Completed or Removed to Removed (Completed for a type with no Removed state), parents before children, signed `[ADO plugin]`. A closed parent cannot roll up and its closed task wakes no one, so children closed after it change nothing. Open pull requests are left alone.
- Only a board user can run either action. The widget also lists Josh's own steps (request changes on the Document once, approve the plan and the breakdown, merge).

## Constraints found that affect later items

- **Task UI (A2, built):** the chip ("ADO #123 · Active", linking to the item) and the link/unlink control are a `toolbarButton` slot on the task (capability `ui.action.register`). Core changes, not a plugin list page, give one task list: a "Linked to ADO" filter (exact `originKind`, the same URL parameter as the routine filter) and search by ADO ID through `origin_id` (only for linked-task origins, case-insensitive). Links are refreshed by events and catch-up (newer revisions only); A2 never creates tasks. A 404 from ADO marks the link "not found in ADO" rather than deleting it; it clears when the item is seen again. The chip is not shown in task list rows. After link or unlink the core task header is not refreshed by the plugin: the plugin UI SDK has no bridge to invalidate host data (the header does not show the origin, so nothing visible is stale).
- **Plugin settings page:** a plugin that adds its own `settingsPage` replaces the generated settings form, including the secret picker. That is why Sync now lives on a dashboard widget.
- **Agent tools (A8):** each call carries the agent and run IDs, so the plugin can enforce per-role permissions and add the `[Name]` prefix itself. The host's tool policies can also limit tools per agent; keep the role mapping in the plugin so it lives in one place.
- **Capabilities:** for a plugin installed by hand, adding capabilities in a later version puts it into `upgrade_pending` until approved. As a shipped plugin (Deploy, below) its declared capabilities are approved with each deploy, so review them in the pull request.
- **SDK fix:** `ctx.http.fetch` failed on any 204 response inside a real worker, though not in the test harness. Fixed in `packages/plugins/sdk/src/worker-rpc-host.ts` and listed with the other fork patches in `CLAUDE.md`.
- **Plugin runtime:** marked early in the spec; plugin code is not sandboxed; the worker does not get proxy environment variables. The Service Bus connection is made by the SDK directly, so it does not appear in the host's HTTP audit like `ctx.http` calls do. Plugin actions time out after 30 seconds. The worker bundle needs a `require` shim (see `esbuild.config.mjs`) because `@azure/service-bus` is CommonJS; the tests run the source, so check `dist/worker.js` loads after dependency changes.
- **Deploy:** settled (backlog D10). The plugin is listed in `scripts/shipped-plugins.json`, so it is built and deployed with the server, installed at startup, and updated and rolled back with each `paperclipai update`; no manual install. How it works: `doc/DEPLOYMENT-STEPS.md`, "How in-repo plugins ship". The LLM Wiki plugin (C2) is added to the same list.

In ADO (`AI Testing`), as the service account, create an "Azure Service Bus" service hook subscription for each of: `workitem.created`, `workitem.updated`, `workitem.commented`, `git.pullrequest.created`, `git.pullrequest.updated`, `git.pullrequest.merged`, and the pull request comment event, filtered to `SimpleRepo` where offered.
